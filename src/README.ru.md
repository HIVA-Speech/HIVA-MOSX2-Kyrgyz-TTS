# MOS-X2 для кыргызского TTS — дизайн эксперимента и сайт

## 1. Что измеряем

**MOS-X2** (Lewis, 2018) — короткая версия опросника MOS-X для синтезированной речи: 4 вопроса, каждый по шкале **0–10** с подписанными краями.

| Шкала | 0 | 10 |
|---|---|---|
| Разборчивость (Түшүнүктүүлүгү) | очень трудно понять | очень легко понять |
| Естественность (Табигыйлыгы) | как робот | как человек |
| Интонация / просодия (Интонациясы) | совсем неестественная | очень естественная |
| Общее впечатление (Үндүн жалпы таасири) | очень неприятный | очень приятный |

Итоговый балл MOS-X2 = среднее четырёх шкал (0–10). Отдельные шкалы тоже анализируются.

> Перед публикацией сверьте точные формулировки с оригинальной статьёй (Lewis J.R., 2018, *MOS-X2*), а кыргызский перевод — с носителем (лучше прямой + обратный перевод).

## 2. Стимулы и план

- **60 записей** = 2 пола диктора × 10 категорий текста (Адабият, География, Жомоктор, Искусство, Медицина, Психология, Саясат, Тарых, Техника, Эпос) × 3 записи. Длина записей 33–51 с (в среднем 42 с).
- Категориям присваиваются коды c01..c10; слушатели названия категорий не видят.
- Внутри ячейки 3 записи = 3 разных текста одной тематики. Мужской и женский голос читают одни и те же тексты, поэтому сравнение голосов не смешивается с различиями текстов.
- **Звучат только первые 12 с** каждой записи, последние 1,5 с — плавное затухание (`MAX_PLAY_S`, `FADE_S` в `config.js`). С ffmpeg `make_stimuli.py` заранее обрезает файлы так же, нормализует громкость (−23 LUFS) и кодирует в MP3 128 кбит/с; без ffmpeg обрезает браузер.

### Распределение по слушателям (рекомендуется)
Каждый слушатель оценивает **20 записей** — по одной из каждой ячейки пол × категория. Три списка (A/B/C) берут запись №1, №2 или №3 соответственно, так что каждый слушатель:
- слышит все 10 категорий обоих полов → сравнения **внутри слушателя**;
- не слышит один и тот же текст многократно в одной категории;
- тратит ≈10–15 мин (4 мин чистого звучания + проверки).

Новый участник автоматически попадает в список с наименьшим числом прошедших (функция `next_list`). Порядок записей случайный для каждого, без двух подряд из одной категории.

Хотите, чтобы все слушали все 60 — поставьте `N_LISTS: 1` в `config.js`.

### Сколько слушателей
Ориентир — **≥ 20 оценок на каждую запись** (ITU-T P.800 рекомендует не меньше 15–20 слушателей) → **≥ 60 прошедших и завершивших** (по 20 на список). Закладывайте +25–30 % на отсев: набирайте ~80.

## 3. Проверка внимания

1. **В начале (вход):** 3 записи, в каждой голос говорит одно число по-кыргызски («жети», «үч», «тогуз»). Участник выбирает цифру 0–9. Нужно 3/3; при ошибке — совет проверить громкость и наушники и **вторая попытка**; после двух неудач тест закрывается (запись участника с `passed=false` сохраняется для статистики отсева). Это же — проверка, что звук вообще работает.
   - Запишите эти 3 файла **живым диктором** с лёгким фоновым шумом (SNR ≈ 10 дБ), чтобы проверка не проходилась без наушников «вполуха».
2. **Проверка понимания кыргызского:** 3 отрывка (разные категории, голоса по очереди), после каждого — выбрать из 4 вариантов фразу из 2–3 слов, которая прозвучала. Нужно ≥ 2/3, иначе тест закрывается (`passed=false`, ответы — в `calib_answers`).
   - Верная фраза берётся из транскрипта (`N.txt`) в пределах первых ≈9 с звучания (по скорости речи файла), 3 ложные — той же длины из других текстов (одна — из той же категории) и в целевом тексте не встречаются. Генерирует `make_stimuli.py`.
   - Отрывки берутся из чужих списков, поэтому в основном тесте слушатель их не встретит.
   - Это синтезированная речь: при плохой разборчивости системы отсев вырастет — учитывайте это при интерпретации.
3. **Пробные примеры:** 2 записи-якоря (живая речь и заведомо плохой синтез) показывают диапазон шкалы. В анализ не идут.
4. **Во время теста:**
   - оценку нельзя поставить, пока запись не прослушана до конца; перемотки нет; число прослушиваний и время ответа сохраняются;
   - в середине — **контрольная запись**: «Бул жазуу көңүлдү текшерүү үчүн. Бардык төрт шкалада 0 тандаңыз.»
5. **При анализе** исключаются: не прошедшие вход (любую из двух проверок), не завершившие, проваленный контрольный вопрос (любая шкала > 1), «прямая линия» (одна и та же оценка везде). По желанию — не носители языка.

## 4. Как устроен сайт

```
index.html               страница и стили
app.js                   логика: согласие → анкета → проверка звука → проверка понимания → пробные → 20 оценок → отзыв
config.js                ключи Supabase (публичный anon), AUDIO_BASE, параметры эксперимента
i18n.js                  тексты (кыргызский / русский)
stimuli.json             список стимулов (генерируется make_stimuli.py, только коды)
supabase/schema.sql      таблицы, права доступа, балансировка списков, бакет для аудио
scripts/make_stimuli.py  voices → stimuli.json (+ MP3, загрузка в Storage и таблицу stimuli)
scripts/analysis.py      исключения, α Кронбаха, средние ± 95% ДИ, смешанная модель

../voices/  (рядом с репозиторием, не в git)
  MOS_test_Male/<Категория>/1.wav 1.txt …   по 3 записи + транскрипты
  MOS_test_female/<Категория>/…
  check/  check_1..3.wav, catch.wav
  train/  natural.wav, low.wav
  categories.json   соответствие код → название (создаётся скриптом)
```

Аудио хранится в публичном бакете Supabase Storage `stimuli` (`m/c01/1.mp3` …), а таблица `stimuli` связывает ID записи (`m_c01_1`) с файлом, названием категории и текстом. `responses.stimulus_id` — внешний ключ на `stimuli.id`; представление `responses_full` выдаёт оценки вместе с данными о записи.

Каждый ответ отправляется сразу; при обрыве связи — копится на устройстве и досылается. Прогресс переживает перезагрузку страницы. Повторное прохождение с того же браузера блокируется. Ссылка вида `…/?pid=ABC123` сохраняет внешний ID (для Prolific/Toloka/вознаграждения); в конце показывается код участника.

## 5. Запуск

1. **Supabase:** создайте проект → SQL Editor → выполните `supabase/schema.sql` (создаст и бакет `stimuli`). В Project Settings → API скопируйте `Project URL` и `anon public` ключ в `config.js`; `service_role` ключ — в `.env` (по образцу `.env.example`, в git не попадает).
2. **Аудио:** установите ffmpeg (MP3 в ~10 раз меньше WAV: на бесплатном тарифе 5 ГБ трафика в месяц) и выполните из корня репозитория `python scripts/make_stimuli.py --upload`.
3. **GitHub Pages:** загрузите репозиторий → Settings → Pages → Deploy from branch `main`, папка `/ (root)`. Сайт: `https://<user>.github.io/<repo>/`.
4. **Пилот** на 3–5 людях: проверьте время прохождения, понятность шкал, что строки появляются в таблицах Supabase. Пилотные данные удалите.
5. Мониторинг — представление `progress` в Supabase (сколько прошло по каждому списку).
6. Анализ: выгрузите `participants` и `responses` (или `responses_full`) в CSV в папку `data/` → `python scripts/analysis.py data`.

### Если нужен Firebase вместо Supabase
Логика та же: коллекции `participants`, `responses`, `feedback`; правила Firestore — `allow create: if true; allow read, update, delete: if false;`; балансировку списков проще делать случайным выбором (`Math.random()*3`) или через счётчик-документ с транзакцией. Учтите, что Cloud Storage для новых проектов Firebase требует платного тарифа Blaze. Supabase удобнее для анализа: данные сразу в SQL и выгружаются в CSV.

## 6. Что сообщать в статье
Число слушателей (всего/исключено и почему), их родной язык и регион, тип наушников, распределение записей по спискам, средние MOS-X2 и по шкалам с 95% ДИ для каждой категории × пол, α Кронбаха, результаты смешанной модели (слушатель и стимул — случайные эффекты), попарные сравнения категорий с поправкой Холма.
